# 트레이더스 실제 화면 수량 박스 높이와 캐시 유실 — 2026-10-08

사용자 제보는 이름이 마미손까지 나오지만 수량·금액 미연결로 대다수 체크가 풀리는 현상이었다. 앱 종료나 상품명 탐색 종료 오류와 구분한다.

## 재현

- 현재 설치 앱의 실제 선택 화면 상태를 디버그 연결로 읽었다. 앨범 `receipt-recreated.png`에 해당하는941×1672px 사진이며 앱 내부 선택 경로는 `scaled_1000000020.png`다.
- 실제 `_select` 호출로 첫 상품 `파실 딥클린 파워젤`, 수량3, 오른쪽80,940원을 골랐다. `_quantityWithSearchArea`에서 현재 화면 크기에 따른 한 글자 여백을 적용했다. 이전 서비스 테스트처럼 임의의 작은4px 사진 여백을 넣지 않았다.
- 첫 상품 `(92,458)~(406,494)`, 실제 수량 검색 박스 `(662.9,455.9)~(695.1,498.1)` 높이 약42.1px, 금액 `(771,462)~(866,492)`이다. 촘촘한 상품 행 간격은 약36px다.
- 수정 전 같은 화면 후보/사진/선택 박스로 실제 ML Kit 이름 열과 자동 연결을 호출하면 검토17개 중 구매15개, 체크5개였다. 금액은 대부분 살아 있지만 촘촘한 행의 수량이0으로 지워졌다. 부분 OCR은0회다.

## 원인과 수정

`readReceiptRegionRepeatedly`의 새 크롭 최소 높이 검사가 기존 성공값을 복사하기 전에 실행된다. 첫 수량 박스42px가36px 행 안에 들어가지 못해 기존 OCR 수량까지 폐기했다. 이전 실사진 서비스 테스트에서 수량 박스를 더 작게 지정해 이 실패를 놓쳤다.

`receipt_automatic.dart`의 자동 필드 읽기는 같은 상품 행으로 검증된 전체/열 OCR 성공값이 있으면 즉시 재사용한다. 새 크롭에 필요한 최소 높이 조건으로 이미 읽힌 숫자를 버리지 않는다. 사용자 박스 높이는 그대로 유지한다. 새 OCR이 필요한 경우의 높이/행 경계 제한, 최대5회/첫 성공, 취소 검사는 유지한다.

## 수정 후 실제 화면 검증

- 동일한 화면 선택과42px 박스로 hot reload 후 재실행: 구매15개 모두 수량·금액이 맞으며 체크, 중간 포인트카드2개만 체크 해제. 이름 열1회·부분 OCR0회, 서비스 호출2.532초(1회 관측).
- 실제 화면의 `_finishAutomatic` 동작을 호출해 검토 화면까지 전환했다. 현재 `ReceiptReviewScreen` 초안에서15개 체크와 같은 수량·금액을 다시 확인했다. 저장은 하지 않았다. 최종 전달 결과는 `review.tsv`다.
- `receipt_accumulation_test.dart`: 첫 수량·금액 박스 높이가 행보다 큰 경우에 값/체크/원래 박스 높이를 유지하고 재OCR하지 않는 회귀2개를 추가했다. 모의 후보 시험이며 위 실제 ML Kit·화면 흐름 검증과 구분한다.
- 전체 테스트220개 통과·기존1개 건너뜀. 상품명 오탈자는 일부 남는다. 이번 수정 코드는 에뮬레이터 실행본에 hot reload로 반영했으며 APK 빌드·재설치는 하지 않았다.
