1. AI 개발 도구와 모델의 구분

AI 개발 도구는 SDK·툴킷·프레임워크·추론 엔진을 포함하는 통칭이다. 모델은 학습된 가중치와 입력·출력 규격이다. 모델 포함 SDK와 직접 모델을 준비하는 추론 런타임은 사용 방식이 다르다.

종류기본 사용 방식
ML Kit — 모바일 ML SDK학습된 모델과 기능 API를 제공한다. 한국어 텍스트 인식 구성요소에 사진을 전달하면 글자·위치를 얻는다. [1] [2]
PaddleOCR — OCR 툴킷OCR 모델과 학습·추론·배포 도구를 제공한다. 선택한 모델을 Paddle Lite나 ONNX Runtime 등 지원 실행 경로에 연결한다. [12] [13] [21]
PaddlePaddle — 딥러닝 프레임워크모델을 정의·학습하고 추론하는 기반이다. 모바일 경량 실행을 맡는 Paddle Lite와 역할이 다르다.
Paddle Lite — 경량 추론 엔진지원 모델을 .nb 형식으로 준비해 모바일에서 실행한다. 입력 생성과 출력 디코딩을 별도로 작성한다. [20] [21]
Vision / Core ML — Apple 프레임워크Vision은 텍스트 인식 등의 영상 분석 API, Core ML은 준비한 머신러닝 모델의 기기 실행 기능을 제공한다. [4] [5]
범용 추론 런타임LiteRT, ONNX Runtime, ExecuTorch는 지원 형식의 모델, 입력 텐서, 출력 해석을 준비해야 한다. [3] [5] [6] [7]

모델을 준비할 때 확인할 항목

  • 언어와 학습 대상: 한국어 상품명, 숫자, 영수증 인쇄 글꼴을 처리할 수 있는가.
  • 입력 규격: 이미지 크기, 채널 순서, 자료형, 정규화, 문자 사전이 무엇인가.
  • 출력 규격: 문자열, 글자 위치, 클래스 점수 중 어떤 결과를 제공하는가.
  • 기기 조건: 지원 연산, 가속기, 모델 파일 크기, 실행 중 메모리, 라이선스가 맞는가.

파일 크기는 실행 메모리와 같지 않다. 가중치 외에도 중간 텐서와 입력·출력 버퍼가 필요하다. 양자화 모델도 런타임과 기기가 해당 연산을 지원해야 실행할 수 있다.

3. Android 기본 사용

ML Kit: 한국어 OCR 모델을 선택해 사진 전달

한국어 인식 구성요소를 앱 의존성에 추가하고 인식기를 생성한다. 모델을 앱에 포함하는 방식과 필요할 때 내려받는 방식의 준비 시점이 다르므로, 첫 실행에서 모델이 준비됐는지 처리한다.

// Kotlin: 한국어 모델 구성요소 의존성 준비 필요
val reader = TextRecognition.getClient(
    KoreanTextRecognizerOptions.Builder().build()
)
val input = InputImage.fromBitmap(receiptBitmap, 0)
reader.process(input)
    .addOnSuccessListener { result ->
        for (block in result.textBlocks) {
            for (line in block.lines) {
                saveCandidate(line.text, line.boundingBox)
            }
        }
    }
    .addOnFailureListener { error -> showReadFailure(error) }
// saveCandidate와 showReadFailure는 앱에서 구현하는 함수다.
// 화면 종료 시 진행 작업을 처리하고 reader.close()로 해제한다.
[1]

LiteRT: 직접 준비한 OCR 모델 실행

지원 .tflite OCR 모델을 준비하고 이미지 → 입력 텐서 → 추론 → 출력 디코딩 순서로 구성한다. 입력 모양·자료형·정규화와 문자 사전을 모델에 맞춘다. 런타임에 사진을 넣는 것만으로 글자 인식이 완성되지는 않는다. PP-OCR 모델을 별도 검증 없이 .tflite로 바로 실행할 수 있다고 가정하지 않는다.

[3]

예제는 핵심 API 흐름을 보여준다. 사진 방향, 모델 설치, import, 수명 관리와 UI 비동기 처리는 실제 앱에서 함께 구성한다.

4. iOS 기본 사용

Vision: 지원 언어 확인 후 글자·좌표 인식

인식 수준과 API 리비전에 따라 지원 언어가 달라질 수 있다. 한국어 지원을 확인한 뒤 요청한다.

import Vision

// 호출자가 이미지 방향을 맞춘 CGImage를 전달한다.
func readReceipt(_ image: CGImage) throws
    -> [VNRecognizedTextObservation] {
    let request = VNRecognizeTextRequest()
    request.recognitionLevel = .accurate
    let languages = try request.supportedRecognitionLanguages()
    guard languages.contains("ko-KR") else {
        throw NSError(domain: "ReceiptLanguage", code: 1)
    }
    request.recognitionLanguages = ["ko-KR", "en-US"]
        .filter { languages.contains($0) }
    try VNImageRequestHandler(cgImage: image).perform([request])
    return request.results ?? []
}
// observation.topCandidates(1).first?.string: 인식 문자열
// observation.boundingBox: 정규화된 영역 좌표
[4] [19]

Core ML: 직접 준비한 모델 실행

학습된 모델을 coremltools로 지원 형식에 변환하고 앱에 포함한다. Xcode에서 생성한 모델 클래스로 입력값을 전달하거나 MLModel API를 사용한다. 이미지 입력, 정규화와 출력 이름은 모델 규격을 따른다.

한국어 OCR 모델을 연결하려면 지원 연산과 변환 성공 여부를 확인하고 글자 검출·인식 출력과 문자 사전을 해석하는 코드를 작성한다. Core ML 자체가 한국어 OCR 가중치를 제공하는 것은 아니다.

[5]

5. 크로스플랫폼 앱 연결

Flutter: ML Kit 플러그인 예시

플러그인은 플랫폼 채널을 통해 Android·iOS 네이티브 SDK를 호출한다. Google이 직접 유지하는 Flutter SDK가 아니므로 플러그인과 네이티브 설치 조건을 함께 확인한다.

final recognizer = TextRecognizer(
  script: TextRecognitionScript.korean,
);
try {
  final input = InputImage.fromFilePath(photoPath);
  final result = await recognizer.processImage(input);
  for (final block in result.blocks) {
    for (final line in block.lines) {
      collect(line.text, line.boundingBox);
    }
  }
} finally {
  await recognizer.close();
}
// collect는 글자와 위치를 보관하도록 앱에서 구현한다.
[9]

Flutter: 직접 모델을 실행하는 방법

tflite_flutter는 Dart FFI로 TensorFlow Lite Interpreter를 연결한다. Interpreter.fromAsset으로 모델을 읽고 getInputTensor·getOutputTensor로 규격을 확인한 뒤 run으로 추론한다. 입력 생성과 출력 디코딩은 앱에서 작성한다.

6. 한국어 OCR 경량 모델

후보모델과 실행 방식
ML Kit 한국어한국어 텍스트 인식 SDK 구성요소. 별도의 학습 가중치 교체보다 제공 API로 글자·위치를 얻는 방식이다. Android와 iOS에 각각 연결한다. [1] [2]
PP-OCRv5 검출PP-OCRv5_mobile_det: 공식 표 기준 4.7 MB. 글자가 있는 영역을 검출하며, 문자열 판독에는 인식 모델이 추가로 필요하다. [12]
PP-OCRv5 한국어 인식korean_PP-OCRv5_mobile_rec: 공식 표 기준 14 MB. 한국어·영어·숫자 인식 모델. 검출된 글줄 이미지와 문자 사전으로 결과를 해석한다. [13]
PP-OCRv3 한국어 인식korean_PP-OCRv3_mobile_rec: 공식 표 기준 9.6 MB. 한국어·숫자 인식 후보. v5와의 정확도·속도 우열은 별도 조건에서 비교해야 한다. [13]
Tesseract 언어 모델kor·eng traineddata를 사용하는 OCR 엔진. tessdata_fast와 tessdata_best의 크기·속도·정확도 특성이 다르다. 별도의 엔진 모바일 연동이 필요하다. [16]

PaddleOCR의 모바일 배포

공식 Android·iOS 배포 예제를 참고해 모델 실행과 이미지 입출력 경로를 구성할 수 있다. Paddle 원본 모델 파일을 ONNX Runtime에 그대로 전달할 수는 없다. 선택한 배포 방식에 맞는 변환 모델, 지원 연산, 전후처리와 문자 사전을 준비해야 한다.

[14] [15]

영수증 모델을 비교할 때의 구분

한국어 상품명은 인식 모델의 언어 지원이 중요하고, 작은 수량은 검출과 인식 모두 영향을 받는다. 전체 사진에서 숫자 위치를 찾는 성능과 지정한 영역에서 숫자를 읽는 성능을 구분해서 조사한다.

위 용량은 문서에 표시된 모델 크기이며 변환·양자화 파일이나 앱 설치 크기와 일치한다고 가정하지 않는다.

7. 메모 사진 OCR과 손글씨 요구

앱 요구사항 F-13~F-16은 촬영·앨범으로 가져온 종이 메모에서 상품명과 수량을 읽고, 사용자가 수정·선택한 결과만 목록에 넘기는 기능이다. 인쇄 메모와 손글씨 메모를 모두 포함한다.

사진 입력에 맞는 OCR 경로

입력 / 후보구현 방법과 확인할 조건
인쇄 메모 사진ML Kit 한국어 또는 Vision 텍스트 인식으로 글자·위치를 받는다. 대안은 PP-OCR 검출 + 한국어 인식 모델의 모바일 실행이다. [1] [2] [4] [12] [13]
한국어 손글씨 사진같은 사진 입력 경로에서 별도 표본으로 시험한다. 한국어 지원이나 인쇄 글자 성적만으로 손글씨 정확도를 보장하지 않는다. 이번 영수증 실험은 손글씨 성적을 측정하지 않았다.
상품명·수량 후보OCR 원문과 줄 위치를 유지하고 이름·숫자 후보를 만든다. 수량이 불명확하면 검토에서 확인받는다. 인식 오류를 임의로 실제 구매 항목으로 확정하지 않는다.
실패·취소빈 결과는 재촬영·다른 사진·직접 입력으로 연결한다. 사진 가져오기 취소나 권한 거부 시 기존 목록을 바꾸지 않는다.

Digital Ink와 사진 OCR의 차이

ML Kit Digital Ink Recognition은 화면에 그린 획의 좌표·시간 데이터를 입력으로 받는다. 이미 찍은 종이 메모 사진을 전달하는 API가 아니므로, 손글씨라는 이유로 사진 OCR 대신 연결하지 않는다.

별도로 확인할 시험

9. OCR 요구사항과 구현 방법

요구사항 분석서 v1.0 중 사진 입력·문자 인식·결과 검토 범위를 다룬다. 목록 연결·구매 확정·저장·동기화·가격 비교의 구현은 이 문서에서 다루지 않는다.

요구사항AI 개발 도구 + 모델 / OCR 화면 구현
F-13 / 메모 사진 입력카메라·앨범에서 사진을 얻어 기기 OCR에 전달한다. 권한 거부와 가져오기 취소는 앱의 입력 처리이며 기존 항목을 유지한다.
F-14 / 메모 문자 인식ML Kit 한국어, Vision OCR 또는 PP-OCR 검출 + 한국어 인식 모델을 실행한다. 사진 손글씨는 별도 검증하고 글자 미검출 시 직접 입력을 제공한다.
F-15~16 / 메모 검토·선택글자·위치 후보를 보여 주고 이름·수량을 수정·제외하게 한다. 사용자가 선택한 확정 결과만 다음 처리에 전달하며 동일 이름을 임의 병합하지 않는다.
F-17 / 영수증 인식전체 OCR의 글자·좌표에서 매장·구매일·상품명·수량·금액 후보를 만든다. 모델은 글자를 읽고, 날짜·숫자 판별과 위치 연결은 앱의 후처리로 구현한다.
F-18 / 구매 정보 검토매장·구매일·상품·수량·금액을 확인·수정한다. 용량·단위·할인 조건은 직접 입력하거나 확인 불가로 표시한다. OCR에 없던 값을 임의 추정하지 않는다.
선택 영역 재인식사진 상자와 후보 버튼에 같은 ID를 연결한다. 지정 영역을 같은 엔진으로 재인식하고 원본 좌표로 환산한다. 실패하면 이전 값을 새 결과처럼 적용하지 않는다.
여러 장·자동 후보장별 ID와 첫 상품 위치를 유지한다. 상대 위치로 상품·수량·금액을 연결하며 불확실한 항목은 체크를 해제한 검토 후보로 남긴다.

OCR 검증 기준

N-03은 자원 준비 후 1,200만 화소 이하 사진의 결과·실패 안내를 10초 이내 표시하는 제안 기준이다. N-07은 원본 사진의 영구 저장·외부 전송을 막고 임시본을 정리하도록 요구한다. N-09는 모든 추출 항목을 확정 전에 수정·제외할 수 있도록 요구한다. 실제 충족 여부는 따로 시험한다.

현재 실험은 상품명·수량·금액 인식 성적이다. 매장·날짜·용량·할인 및 위 화면·보호·응답 기준의 통과를 의미하지 않는다.

10. 영수증 후보 데이터 예시

문자열과 위치를 함께 유지

아래는 “퍼실 / 수량 3 / 금액 80,940”을 읽었다고 가정한 데이터 예시다. 좌표는 설명용이며 실제 사진의 인식 결과가 아니다.

{
  "photoId": "first-photo",
  "imageWidth": 1200,
  "imageHeight": 1800,
  "candidates": [
    {"id": "name-01", "text": "퍼실", "box": [100, 400, 180, 440]},
    {"id": "qty-01", "text": "3", "box": [650, 445, 670, 475]},
    {"id": "amount-01", "text": "80,940", "box": [850, 445, 980, 475]}
  ]
}
// box: [왼쪽, 위, 오른쪽, 아래]의 원본 사진 픽셀 좌표

서로 다른 엔진의 좌표를 맞추는 방법

Vision의 정규화 좌표는 아래쪽 원점이므로 사진 폭 W, 높이 H에 대해 left = x × W, top = (1 − y − h) × H, width = w × W, height = h × H로 바꾼다. 입력 방향과 표시 방향을 동일하게 처리한 사진을 기준으로 사용한다.

[4]

부분 OCR에서는 잘라낸 영역의 왼쪽·위쪽 위치를 결과 좌표에 더한다. 크롭 이미지를 별도 크기로 입력했다면 그 배율을 먼저 되돌린다. 화면 확대·이동은 표시 변환이며 저장한 사진 좌표를 직접 바꾸지 않는다.

숫자와 검토 상태

“12,000”은 전체 토큰에서 12000으로 해석하고 음수 부호를 보존한다. 금액의 점·콤마 처리는 금액 입력 문맥에서 검증하며 “1L”·“850g”은 용량 후보로 유지한다. 동일한 “1”도 위치가 다르면 다른 ID를 부여한다. 값이 없으면 사용자 확인 전 임의로 수량 1을 확정하지 않는다.

12. 사전 독립 비교 — 실행 환경 차이

실제 영수증을 ML Kit·PaddleOCR·Tesseract에 각각 입력했다. 한 엔진의 결과로 다른 엔진의 빈 값을 보충하거나 결과를 합치지 않았다. 아래 수치는 저장된 실행 원문을 다시 집계한 결과다.

엔진실제 시험 구성
ML KitAndroid 에뮬레이터에서 네이티브 한국어 OCR 실행. Flutter 플러그인 0.16.0, 한국어 구성요소 16.0.1. 앱의 자동 연결·열 탐색·재시도는 호출하지 않았다.
PaddleOCRUbuntu 호스트 CPU에서 PaddleOCR 3.4.0 / PaddlePaddle 3.2.2 실행. PP-OCRv5_mobile_det + korean_PP-OCRv5_mobile_rec. CPU 4스레드, MKLDNN 해제. Paddle Lite·ONNX 모바일 실행 성적은 아니다.
TesseractUbuntu 호스트 CPU에서 4.1.1 / kor+eng / OEM 1 실행. 기본 PSM 3과 별도 PSM 7·PSM 10 설정을 구분했다.

동일 입력과 정답

교보 첫째 장 8개, 둘째 장 11개, 삼선 2개 상품을 직접 확인해 정답으로 지정했다. 전체 사진, 수량·금액 단독 크롭, 숫자 행 크롭을 각 엔진에 동일 파일로 입력하고 SHA-256을 검사했다. 공통 대비·확대·기울기 처리는 추가하지 않았다.

채점 기준

단독 숫자는 천 단위 점·콤마를 정규화한 뒤 정답 하나와 일치해야 성공이다. 올바른 숫자 외에 다른 숫자가 추가되면 실패로 센다. 전체·행 입력은 엔진의 박스 중심이 사람 지정 정답 영역 안에 있는지와 값이 맞는지를 함께 확인한다. 다른 행의 같은 숫자는 정답으로 가져오지 않는다.

상품명은 공백·기호·대소문자를 제외하고 글자·숫자를 비교한다. 완전 일치와 문자 편집 오류율을 함께 제시한다. 상품 후보 병합과 최종 자동 연결 정확도는 이 시험에 포함되지 않는다.

기기 비교의 범위

입력은 같지만 실행 장치와 런타임이 다르다. 현재 결과는 해당 구성의 OCR 인식 비교이며, 휴대폰 속도·발열·메모리·APK 용량 순위로 해석할 수 없다. iOS 실행과 실기기 Paddle 배포 성능은 미측정이다.

원본 사진은 334×598px다. 수량·금액·행 크롭 45건이 ML Kit 최소 입력 크기 조건에 걸렸다. 이를 글자 오인식과 구분했다. 각 변 최소 32px가 되도록 동일 흰 여백을 붙여 세 엔진을 다시 실행했다. 확대·대비 변경은 하지 않았다. 각 엔진의 추가 45건에서 실행 오류는 0건이었다.

공통 여백 입력ML KitPaddleOCRTesseract PSM 3
수량 단독 영역2/157/150/15
금액 단독 영역12/1512/152/15

해석과 남은 비교

입력 오류가 없어져도 인식 성공이 보장되지는 않았다. 수량 단독 영역은 ML Kit 2/15, PaddleOCR 7/15로 여전히 놓치는 숫자가 있었다. 전체 입력, 단독 영역, 행 입력 성적을 한 숫자로 섞으면 이런 차이를 잃는다.

이어지는 절에서는 세 엔진을 모두 같은 Android 에뮬레이터에서 새로 실행한다. 휴대폰 속도·발열·최대 메모리·엔진별 설치 용량은 별도 실기기 측정이 필요하다. 기술 교체나 최종 선정 결론은 내리지 않는다.

15. 동일 Android 기기에서 독립 실행

세 엔진을 모두 Android 15 / API 35 / x86_64 에뮬레이터에서 새로 실행했다. 동일한 사진·영역 217개와 공통 여백 입력 45개를 엔진마다 SHA-256으로 확인했다. Tesseract 추가 설정을 포함해 8회, 총 1,059건을 실행했다. 한 엔진이 놓친 값을 다른 엔진으로 보완하거나 결과를 합치지 않았다.

앱에 연결한 방법

Flutter 전체·부분 OCR의 공통 인식기에서 빌드별로 한 엔진을 고른다. ML Kit는 기존 플러그인, Paddle·Tesseract는 Android 플랫폼 채널로 호출한다. 글줄·단어의 원래 상자와 점수를 Flutter에 반환하며 임의로 단어를 나누거나 다른 엔진으로 재시도하지 않는다.

사전 시험과 달라진 조건

Paddle은 PaddlePaddle 대신 ONNX Runtime을 사용하고 내부 검출 최대 변을 4000px에서 1600px로 제한했다. 입력 사진 파일과 반환 좌표는 원본 기준이다. Tesseract 코어는 4.1.1에서 5.5.1로 달라졌다. 같은 모델 가중치·언어 파일이라도 이 구성 차이가 성적을 바꿀 수 있다.

별도 비교 패키지: com.todayone.todo.ocrcompare2. 기본 앱은 ML Kit를 유지한다. 원문·모델 해시·버전·실행 로그는 docs/ocr-comparison/20261012-android/에 보관했다.

배포 과정에서 실제 확인한 실패

Paddle SDK의 예제 OpenCV 4.5.3은 x86_64 라이브러리 로딩 오류가 있었다. 비교 모듈에서 공식 OpenCV 4.12.0으로 연결했다. Paddle 모델의 이미지 입력을 준비하고 검출 상자를 처리하는 데 사용한다. [24]

4000px 검출은 12MP 원본에서 Java 메모리 부족으로 종료됐고, 메모리 한도 확대 후에도 프로세스 메모리 약 1.9GB에서 종료됐다. 최종 비교는 한도 확대 없이 1600px 검출을 사용한다.

해석 범위

모두 Android에서 실행했지만 에뮬레이터 결과다. 실기기·iOS, 손글씨·매장·구매일 정확도, 발열·최대 메모리·엔진별 설치 용량은 미측정이다. 디버그 호출 시간은 입력 크기와 엔진별 빈 결과에 영향을 받으므로 휴대폰 속도 순위로 제시하지 않는다. 최종 기술 선정은 하지 않는다.
