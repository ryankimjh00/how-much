### 영수증 OCR 단계적 이식 — 3단계

- 사용자 수정 지시에 따라 develop에 없는 할인 입력·할인액 필드는 추가하지 않는다. `PurchaseData`, 로컬 JSON, 서버 API·Swagger와 인증·동기화 구현은 그대로 유지한다.
- 상품명 선택 후 “입력할 금액은 어디에 해당하나요?”에 “단가 / 단가 아님”으로 답한다. 답변과 금액 선택 전에는 수량 단계로 넘어가지 않는다. 입력 방식은 선택한 영수증 항목 전체에 적용한다.
- 단가 입력은 수량 선택 사항·생략 시 1개이며 결제금액은 단가×수량이다. 총액 입력은 수량을 반드시 선택하거나 직접 입력하며 총액을 그대로 기록한다. 자동으로 수량 1을 확정하지 않는다. 상품별 수량 후보는 금액 후보와 별도 사본이며 길게 눌러 수정할 수 있다.
- 금액·수량의 직접 입력을 제공한다. 수량은 1~999개, 결제금액은 0~9,999,999원 범위를 검사하고 단가×수량의 한도 초과도 거부한다. 취소하면 확정 전 입력을 버리고 이전 선택을 유지한다.
- 예: 단가 26,980원·수량 3과 총액 80,940원·수량 3은 모두 기존 저장 모델의 quantity=3, total=80940으로 전달되어 개당 26,980원이 된다. 한 포장당 낱개 수를 지정한 경우에는 develop의 기존 규격 가격 계산도 유지한다.
- 기존 검토 목록·편집창에서 개당 가격을 표시한다. 편집창은 사본에서 입력하고 “확인했어요”에서만 확정하여 닫기·취소 시 기존 값을 유지한다. 검토 목록에는 투명 Material을 추가해 기존 카드 장식과 ListTile 터치 효과를 유지한다.
- 검증: 새 3단계 테스트 7개와 전체 Flutter 테스트 46개 통과. 320×568 화면과 키보드 상태의 수량 직접 입력도 통과. 단가/총액 계산, 수량 누락·잘못된 입력·곱셈 초과, 직접 입력·수량 후보 수정 취소, 검토 편집의 취소·확정, 로컬 저장·복원, JSON 왕복 모의 동기화·서버 실패 시 보존을 확인했다. 실제 영수증 OCR과 실서버 검증은 미실시다.
- 정적 분석은 기존 `screens.dart:785` 경고 1개만 남으며 새 코드 지적은 없다. 형식·diff 검사 통과. 패키지 준비·업그레이드·커밋·푸시·APK 빌드·기기 설치는 실행하지 않았다.

### 영수증 OCR 단계적 이식 — 2단계

- 촬영/앨범 OCR 결과가 있으면 `ReceiptSelectionScreen`에서 상품명들을 먼저 선택하고 각 상품의 금액을 차례로 연결한다. 직접 입력은 기존 검토 화면을 유지한다.
- 첫 상품명은 전체 후보에서 고른다. 이후 후보는 첫 이름의 왼쪽 시작점(글자 높이의 1.5배 이내)과 아래쪽 위치로 좁힌다. 기준 상품명을 해제하면 기존 선택도 해제하여 전체 후보에서 다시 고른다.
- 금액은 같은 행과 아래 두 실제 OCR 행에서 모으고, 오른쪽 여부 → 행의 가까움 → 같은 행의 오른쪽 끝 순으로 한 목록에 표시한다. 음수 할인은 이 단계의 결제금액 후보에서 제외하며 원문에는 보존한다.
- 사진 확대·이동, 얇은 1px 박스와 후보 버튼은 같은 ID와 선택/수정 함수를 사용한다. 이름·금액은 길게 눌러 수정하고 적용 전 입력을 검증한다. 사진을 열지 못해도 후보 버튼은 유지한다.
- 금액 후보 수정은 상품별 사본에만 반영한다. 수정 대화상자 취소·전체 선택 취소는 원본 초안과 OCR 결과를 바꾸지 않는다. 선택 완료 시 새 초안만 기존 검토 화면에 전달하며 인증·동기화·저장 모델은 변경하지 않는다.
- 수량·할인과 단가/총액 질문은 3단계 범위다. 현재 선택한 금액은 기존 모델의 total로 전달되며 수량은 기존 기본값 1이다. 실제 수량을 자동 인식해 확정했다는 의미가 아니며 저장 전 기존 검토에서 수정해야 한다.
- 검토 화면의 사진·피드백 박스, 부분 OCR, 이름 영역 병합, 전체 자동과 이미지 보정은 이번 단계에 포함하지 않는다.
- 테스트는 합성 좌표·생성한 사진을 사용하며 실제 영수증 OCR 정확도 검증과 구분한다. 기존 패키지·환경 변경은 유지하고 이번 단계에서 pub get·패키지 업그레이드·빌드·설치·커밋·푸시를 하지 않는다.
- 검증 결과: 2단계 테스트 5개 통과, 전체 38개 통과·기존 UI 테스트 1개 실패(`ListTile`/Material 오류). 분석은 기존 `screens.dart:785` 경고 1개이며 새 코드 지적은 없다. 형식과 diff 검사 통과. 390×844 합성 사진 표시와 320×568·키보드 상태를 확인했다. 실기기·실제 영수증 인식 결과는 미검증이다.

### 영수증 OCR 단계적 이식 — 1단계

- 기반: develop `a12a743`, 작업 브랜치 `feat/receipt-ocr`. 이전 `how-much-fresh`는 읽기 참고만 사용한다.
- 연결: 촬영/앨범 → `OcrService.recognizePath` → `ReceiptDraft.ocrResult` → 기존 검토 화면. 기존 문자열 파서와 저장 흐름을 유지한다.
- `receipt_ocr.dart`에 전체 원문·사진 경로·OCR 줄/단어 좌표와 위치별 후보 ID를 보관한다. 같은 이름/숫자도 원본 위치별로 구분하고 후보와 원본 목록은 수정할 수 없게 한다.
- `12,000`은 12000, `-15,000`은 -15000으로 읽는다. 가까운 같은 줄의 콤마/부호 조각만 결합하며 용량 `1L`, `850g`은 숫자 후보로 변환하지 않는다. 원본 단어는 결합 후에도 보존한다.
- 후보는 상품/결제금액으로 확정하지 않는다. 상품명 병합·수동 선택·수량/할인 계산·사진 표시·부분 OCR·전체 자동·이미지 보정은 포함하지 않는다.
- 사진 경로는 선택/촬영 플러그인이 반환한 이번 검토용 임시 파일이다. 좌표는 ML Kit에 전달한 그 사진의 픽셀 좌표이며, 원래 앨범 파일이 리사이즈되었다면 그 파일의 좌표와 다를 수 있다. 파일을 보정하거나 별도로 확대하지 않는다.
- 저장 모델 `PurchaseData`, 로컬 직렬화, 서버 요청에는 OCR 결과를 추가하지 않는다. 앱 재시작 후 OCR 사진/좌표 복원은 이번 범위에 없다.
- 검증은 합성 OCR 좌표와 모의 네이티브 응답으로 숫자 처리·위치 구분·ML Kit 변환·기존 초안 반환·실패 시 인식기 해제를 확인한다. 실제 사진 인식 품질 검증과 구분한다.
- 검증 결과: 새 OCR 테스트 7개 통과. 최종 전체 테스트는 33개 통과·기존 UI 테스트 1개 실패(`ListTile`의 Material 조상이 DecoratedBox에 가려지는 오류). 정적 분석은 기존 `screens.dart:784` 경고 1개이며 새 코드 지적은 없다. `dart format`과 `git diff --check` 통과. 실제 사진·빌드·기기 설치는 이번 단계에서 실행하지 않았다.
- 작업 전 변경: `analysis_options.yaml`, `pubspec.lock`의 패키지 준비 자동 변경과 Android `gradle.properties` 환경 변경. 앞선 종료 수정에서 Android/iOS 한국어 모델 의존성을 이미 추가했다. 1단계에서 패키지 준비·업그레이드·빌드·기기 설치를 실행하지 않는다.

### 2026-10-06 — fresh 비교 후 선택 진입 조건 보완

- 요청: 검토된 세 문제 중 fresh에도 있는 문제는 유지하고, 이식 과정에서 달라진 부분만 수정.
- fresh는 OCR 원문이 비었을 때 중단하고 문자열 파서의 lines.isEmpty로는 중단하지 않는다. 새 OcrService도 이 기준으로 맞춰 카드케이스처럼 문자열 파서가 제외한 항목의 좌표 후보를 선택 화면에 전달한다. fresh 자체는 별도의 후보 메타데이터 필터로 카드케이스를 제외하므로, 해당 예시의 후보 결과까지 양쪽이 동일하다는 뜻은 아니다.
- fresh 직접 실행 비교: 높이20·가로간격60의 `12,`/`000`에서0만 남음, `850`/`g`에서850이 숫자 후보에 포함됨. 임시 합성 테스트2개로 재현. 사용자 지시에 따라 새 receipt_ocr.dart의 해당 처리와 기존 기대값은 변경 안 함.
- 검증: 프로젝트 전체48개 테스트 통과(기존47+새 진입회귀1), fresh비교 임시2개 통과. 새 회귀는 모의 네이티브 응답에서 빈 문자열초안+좌표후보 반환 및 빈 OCR 거부·인식기 정리를 확인한다. 실제 기기·사진·서버 검증은 아님.
- 정적 검사: 기존 screens.dart:785 unawaited_return_in_try_block 경고1 유지, 새 지적 없음. 수정 Dart format 및diff검사 완료. 패키지준비·빌드·설치·커밋·푸시 안 함.

#### 직접 재현한 차이

- 같은 단일 토큰 `12,000`→12000, `-15,000`→-15000, `1L`/`850g`→숫자 후보 없음은 양쪽 동일하다.
- 단일 토큰 `12, 000`, `12，000`: fresh는12000, 현재는 숫자 후보 없음. `−15,000`, `－15,000`: fresh는-15000, 현재는 숫자 후보 없음. 이는 fresh와 공유하는 아래 조각 문제와 별개다.
- `12,`(x10~40), `000`(x100~130), 높이20의 넓게 분리된 두 토큰은 양쪽 모두0만 남는다. `850`과`g`가 분리되면 양쪽 모두850이 숫자 후보로 남는다. 이 두 공통 문제는 이전 사용자 지시대로 수정하지 않았다.
